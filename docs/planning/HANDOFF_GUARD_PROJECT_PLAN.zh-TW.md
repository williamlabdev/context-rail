## 01 計劃摘要與成功條件

Handoff Guard 協助軟體導入與顧問服務團隊處理交付承諾的變更。使用者匯入已確認的交接文件、新郵件與既有任務，系統辨識期限、需求範圍及負責人的差異，顯示原文依據與受影響工作，再由專案負責人確認並更新任務。

三週的主要交付是一條可驗證的完整流程：匯入資料、分析變更、查看依據、確認提案、保存任務更新、查閱執行結果。第一版以應用內的任務資料庫完成實際寫入；Google Sheets 串接列為有剩餘容量時的擴充。

本計劃的競爭假設是，文件之間的衝突、未正式接受的要求，以及資料改版後失效的核准，是一般交接整理容易遺漏的部分。這個假設需透過使用者訪談和比較測試驗證。所有效率、正確率及成本數字均為規劃目標或預算，尚無產品實測成果。

主要未定事項為兩位成員的實際工時分配、可訪談的使用者、Google Cloud 帳號與模型可用性，以及主辦方對日期、智財與通用套件使用的說明。這些事項納入第一週的工作，不視為已完成。

## 03 使用者與問題驗證

首要使用者是同時閱讀交接文件、回覆客戶並調整工作清單的專案經理。團隊主管或服務交付主管是潛在採購決策者。目標公司的規模、案件量和付費意願屬市場假設，第一週不以未驗證的市場數字作產品決策。

第一個情境限定為一個專案收到新要求後的交付變更。常見問題包括同一交期出現在不同文件中、額外功能沒有更新工作清單、責任歸屬不明，以及新的客戶要求被誤當成已接受的承諾。產品需要辨識這些狀態並支持負責人決策。

### 第一週訪談

預約三位有實際交接經驗的 PM 或服務負責人，每人約 25 分鐘，請對方重述最近一次案例。取得同意後記錄流程、耗時、遺漏及後果；公開資料另行處理授權。

1. 最近一次客戶改交期或增加需求時，資訊散落在哪些地方？
2. 誰決定是否接受變更，接受後由誰更新任務？
3. 整理到可以做決定大約花多久，哪些步驟最耗時間？
4. 曾漏掉什麼內容，後續造成哪些返工或協調？
5. 什麼依據會讓你信任系統的提醒，什麼情況一定要自行查原文？
6. 願不願意用一個合成或經授權處理的案例試用，並再次回饋？

選題確認目標為：至少兩位受訪者能描述反覆出現的相似問題，至少一位願意試用，且能整理三個足以重現痛點的案例。這是內部選題標準，不能當成市場普遍性的證明。若缺乏外部使用者，改由兩位成員以自身可描述的真實流程建立案例，並在成果中標示便利樣本的限制。

## 04 產品流程與功能範圍

### 代表案例

一份已確認的交付計劃約定 10 月 20 日上線，任務清單包含開發、測試與驗收。新的客戶郵件希望提前至 10 月 10 日，並加入單一登入功能。系統指出兩項變更及其來源，顯示受影響任務，並提醒新的要求尚未被團隊接受。PM 可接受、修改或要求澄清，再確認實際要套用的任務更新。

日期均為展示情境，並非實際客戶承諾。流程的完成條件是資料保存成功且重新載入後可看到一致的結果，不能只顯示成功訊息。

### 第一版必要功能

| 編號 | 功能 | 驗收重點 |
| --- | --- | --- |
| F01 | 建立專案與匯入資料 | 文件與任務歸屬正確；格式不符有清楚錯誤 |
| F02 | 抽取交付承諾 | 項目、日期、負責人及原文依據可檢查 |
| F03 | 比較三類變更 | 期限、需求範圍、負責人差異可逐項查看 |
| F04 | 顯示影響與不確定事項 | 有依據的任務關聯與待確認建議分開呈現 |
| F05 | 編輯與確認提案 | 修改內容會生成新版提案，核准綁定確切版本 |
| F06 | 保存任務更新與結果 | 後端檢查身分、版本及重複請求，再交易寫入 |
| F07 | 展示與專案隔離 | 每位展示使用者有獨立合成案例與資料範圍 |

匯入上限先設定為每案五份文字型 PDF 或文字資料、合計 30 頁或 30,000 字元、單檔 5 MB，以先達到的限制為準。任務匯入使用固定 CSV 欄位，上限 50 筆；單次更新最多 20 筆。這些是開發範圍設定，須在第一週以實際模型上下文與延遲測試調整。

首版採英文 UI 與英文展示案例。資料不足時以待確認呈現；負責人可提供補充資料或手動填寫，系統保留其人工修改來源。文件中的「已核准」字樣可作證據候選，不能直接授予系統內的執行權限。

### 擴充的進入條件

只有第二週核心驗收完成，且保有至少 12 人時緩衝，才考慮一個指定 Google Sheets 串接。跨語言案例、掃描文件辨識、語音會議、更多企業連接器及自動排程，列入賽後候選。首版需要完整完成目前定義的工作流程。

### 操作介面

介面由專案資料頁、變更檢閱頁與執行結果頁組成。檢閱頁同時顯示來源、差異與建議更新，使用者能從任務回到原文。執行前顯示更新前後的欄位、待解決問題及此次套用筆數。更新成功後提供可追溯紀錄；失敗時顯示可執行的下一步。

## 05 技術架構與 AI 設計

前端使用 React 與 TypeScript，後端使用 Python 與 FastAPI。前端靜態資源與 API 可由同一個 Cloud Run 服務提供，減少部署組件。由後端呼叫 Google Cloud 上的 Gemini API，Firestore 保存專案與工作狀態，Cloud Storage 保存文件，Firebase Authentication 提供使用者身分。

| 元件 | 責任 | 選用理由 |
| --- | --- | --- |
| React 與 TypeScript | 工作台、來源檢閱、提案編輯 | UI 狀態清楚，便於兩人分工 |
| FastAPI 與 Cloud Run | API、分析流程、權限及執行 | 單一服務先完成雲端端到端交付 |
| Gemini API | 語意抽取、差異與影響候選 | AI 直接處理非結構化工作資料 |
| Firestore | 文件版本、提案、任務與執行紀錄 | 支援交易型更新及版本條件檢查 |
| Cloud Storage | 原始文件與解析產物 | 原文依據可保留及重新查閱 |
| Firebase Authentication | 登入與身分 token | 後端可驗證呼叫者身分 |

資料流程為：使用者匯入資料 → 後端驗證與建立版本 → Gemini 抽取與比較 → 程式驗證輸出 → 使用者檢閱 → 後端交易更新任務 → 回讀結果。模型分析在資料庫交易之外完成，避免交易重試時重複呼叫模型。

### 模型與提示詞

第一天以五個開發案例比較帳號可用的兩個穩定版 Flash 候選模型，按正確率、延遲及每案用量選定，鎖定模型識別與 SDK 版本。三週內以同一模型完成主要比較；若必須更換，重新執行受影響評估並記錄原因。

分析採可追蹤的有限步驟：先抽取各文件的承諾候選，再比對既有已確認基線，最後產生差異與任務更新候選。模型輸出固定 schema，包含來源識別、片段、欄位、舊值、新值及待確認事項。Structured output 支援固定結構，但不能代替語意正確性驗證。[Google 文件](https://docs.cloud.google.com/gemini-enterprise-agent-platform/models/capabilities/control-generated-output)

程式確認來源確實存在、片段能在對應版本找到、任務識別有效、日期可解析、更新欄位在允許範圍內。來源可回查並不代表推論一定正確，因此評估仍須人工檢查原文是否支持主張。

每次只處理當前專案的限定資料包。首版以清楚的來源標記與資料版本完成上下文管理；更多專案或大型資料集需要的檢索系統，依後續量測決定。Agent Development Kit 可在團隊熟悉時導入，但不是本計劃的必要依賴。[ADK 部署參考](https://adk.dev/deploy/cloud-run/)

## 06 資料契約與執行行為

以下是開發所需的最小資料契約，實作時可增加索引欄位，但不得改變來源、核准與執行之間的關係。

| 資料 | 必要內容 |
| --- | --- |
| Project | 專案識別、成員與角色、資料版本、任務集合版本 |
| SourceDocument | 專案、文件版本、檔案雜湊、類型、解析片段、匯入時間 |
| EvidenceRef | 文件識別與版本、片段識別、原文字段與位置 |
| Commitment | 承諾內容、欄位值、來源、是否已由人員確認 |
| ChangeProposal | 專案資料快照、提案版本、更新內容雜湊、差異、待確認事項 |
| ReviewRecord | 審核者、決定、核准的提案版本與雜湊、時間 |
| ActionReceipt | 請求識別、套用的提案、更新前後內容、結果與時間 |

來源增加或改版時，同步增加專案資料版本。任務被其他人修改時增加任務版本。提案綁定分析時的這些版本；使用者修改提案內容後，產生新的提案版本與內容雜湊。

### 確認與套用

介面以「確認並更新」完成一個操作。後端在同一個 Firestore 交易內讀取成員權限、專案版本、提案與任務版本，確認核准的正是畫面顯示的內容，再保存 ReviewRecord、任務修改及 ActionReceipt。來源或任務版本不符時，回傳需要重新檢閱，保留原有任務。

重複請求使用相同 idempotency key，回傳既有結果。Key 若被用於不同內容則拒絕。Firestore 交易可能重試，交易內僅執行資料檢查及資料庫讀寫，不呼叫模型或外部系統。[Firestore 交易文件](https://firebase.google.com/docs/firestore/manage-data/transactions)

提案狀態至少包含 DRAFT、READY、NEEDS_CLARIFICATION、STALE、APPLIED 及 REJECTED。只有 READY 且無阻塞事項的提案可被確認並套用。已完成的操作以紀錄回查；修正錯誤更新需建立新的提案，保留變更歷史。

### 最小 API

| 操作 | 路徑與目的 |
| --- | --- |
| 匯入 | POST /api/projects/{id}/sources，建立資料版本 |
| 分析 | POST /api/projects/{id}/analyses，回傳分析識別與提案 |
| 檢閱 | GET /api/proposals/{id}，取得依據、差異與快照版本 |
| 修訂 | PATCH /api/proposals/{id}，條件式建立新版提案 |
| 套用 | POST /api/proposals/{id}/apply，驗證版本並交易更新 |
| 結果 | GET /api/actions/{id}，回查更新結果與前後內容 |

所有 API 由後端驗證身分與專案權限，不能只依靠前端按鈕。Firebase token 驗證可依官方 Admin SDK 實作；專案成員授權仍是應用責任。[Firebase 身分驗證文件](https://firebase.google.com/docs/auth/admin/verify-id-tokens)

## 07 資料保護與展示環境

公開展示採合成專案資料。訪客可進入獨立展示空間並以限定角色測試，彼此資料隔離，不能讀寫其他專案。真實試用資料另置於受邀空間，預設不進入公開 repository、影片或執行日誌。

原始文件視為分析資料，文件中的指令不會授予工具或系統權限。模型只能產生受限欄位的提案，沒有直接寫入、寄信、刪除或任意網路存取能力。日期與人名缺漏保留待確認，不用模型自行產生的信心百分比作核准條件。

後端使用專用 service account。憑證透過受控設定提供，公開程式碼僅附環境變數名稱與範例。使用伺服器端 SDK 的操作須在每個入口實作專案授權，不能假定用戶端資料庫規則會代替後端授權。

### 最低必要檢查

- 使用者甲無法透過替換識別碼讀取或套用使用者乙的提案。
- 未授權角色直接呼叫套用 API 也會被拒絕。
- 文件內的惡意指令不會造成資料外傳或繞過確認流程。
- 已過期的提案、重複點擊及並行更新不會造成靜默覆寫。
- 檔案大小、格式、單案頁數與每個展示空間的呼叫次數受限。

日誌主要記錄 request ID、模型識別、提示詞版本、耗時、用量與結果分類。公開展示案例可保留至評審結束，訪客臨時資料規劃七天後進入到期清理，須驗證文件與資料庫紀錄一併處理；受邀試用資料的保存期需與提供者確認。來源存取及刪除都須遵循專案權限。

若增加 Google Sheets 串接，外部寫入採可追蹤的工作佇列與重試設計，並先處理重複寫入及部分失敗。外部系統寫入不能宣稱與 Firestore 更新具有同一個原子交易；只在完成寫入與回讀後顯示成功。

## 08 測試設計與驗收指標

建立 30 個案例包，分為 20 個開發案例與 10 個保留案例。每包包含原始交接資料、新要求、既有任務及人工標註答案。以來源情境分組後切分，避免同一案例的小幅改寫同時出現在兩組。第一週由 B 整理標註，A 可查看開發組；保留組至版本固定後才用於最終評估。

案例類型包括沒有變更、日期衝突、範圍增加、責任不明、文件改版與混合例外。至少加入無法得出結論、表面文字不同但意義相同，以及沒有可支持依據的案例，避免測試只涵蓋容易成功的情境。

### 比較方法

品質比較使用相同資料與答案，評估人工處理、同一模型加完整單次提示詞，以及 Handoff Guard 原型。直接模型基線的提示詞也需正常調整至合理品質，並保留內容與參數，避免刻意設置弱基線。

時間比較另安排三至五位使用者，以相近難度的配對案例及交錯順序測試，降低重複看過答案的學習效應。記錄從取得資料到完成可接受更新的總時間，包含閱讀、模型等待、人工修正及確認。整理中位數、範圍與樣本數，不只挑選最快的一次。

| 指標 | 計算方式 | 初始驗收目標 |
| --- | --- | --- |
| 交接時間改善 | 配對案例的人工時間與輔助時間差，再除以人工時間 | 中位數改善至少 50% |
| 衝突 Precision | 正確辨識的衝突數除以所有衝突提醒數 | 至少 90% |
| 衝突 Recall | 正確辨識的衝突數除以人工標註衝突總數 | 至少 90% |
| 主張有來源支持 | 人工判定原文支持的關鍵主張數除以關鍵主張總數 | 至少 95% |
| 任務影響辨識 | 正確任務關聯的 Precision 與 Recall | 兩者至少 85% |
| 完整流程成功 | 在規定輸入內完成分析與一次正確更新的案例比例 | 至少 90% |
| 分析延遲 | 暖機與冷啟動分開，記錄中位數及 P95 | 暖機 P95 先以 60 秒為目標 |

分母為零時記錄 N/A；必須同時公開原始計數、案例數與失敗例。小樣本 P95 僅供原型調校。合成案例結果不能等同真實企業成效，使用者研究也需標示樣本來源。

權限、版本及防重複更新是發布前必要條件：測試中不得出現未核准寫入、跨專案存取、過期提案套用或重複修改。另測模型逾時、無效格式、虛構來源、錯誤任務識別及交易重試。這些檢查的通過僅代表既定測試範圍。

版本固定後，每個保留案例跑三次以觀察模型變異，分別報告單次及整體結果。若看過保留組後再調整提示詞，該組轉為開發資料；補充新的未見案例才能再做最終比較。保存 commit、模型、提示詞、案例版本、原始回應、評分與用量。

### 英文摘要草稿

Handoff Guard is a proposed delivery change assistant for software implementation and consulting teams. It helps project managers compare approved handoff documents, new customer requests, and existing tasks. The system identifies changes to dates, scope, and ownership, links each finding to its source, and prepares a task update for human review.

The prototype will distinguish a requested change from an accepted commitment. Reviewers can inspect evidence, correct the proposal, and confirm the exact update. The application will check permissions and document versions before saving changes. Repeated requests will return the recorded outcome rather than applying the update again.

The planned Google Cloud implementation uses Gemini for language understanding, Cloud Run for the application, Firestore for workflow state, Cloud Storage for documents, and Firebase Authentication for identity. Evaluation will compare manual work, a direct Gemini baseline, and the complete prototype using held-out cases and a small user study. Results will report observed accuracy, completion time, cost, and limitations.

Project managers often receive a new delivery request through email while the approved plan and task list still describe an earlier agreement. They have to work out what changed, which tasks are affected, and what the team has actually accepted.

In this example, the approved plan says October twentieth. A new email asks for October tenth and adds single sign-on. Handoff Guard identifies both changes and shows the original passages beside the affected work.

The new email is a request. The reviewer decides whether to accept it. Here, we inspect the evidence, correct the proposed task update, and confirm the exact changes. The application saves the tasks and displays the recorded outcome. Reloading the page shows the same result.

Now consider a document arriving after review has started. The proposal is marked for another review because its source version has changed. Missing ownership is also shown as a question for the team to resolve.

Our evaluation compares manual handling, direct Gemini use, and the complete workflow. The results shown here will include the number of cases, observed processing time, and errors. Gemini performs the document analysis, while our application controls permissions, review, and task updates on Google Cloud.
